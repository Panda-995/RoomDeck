# RoomDeck 存储、投屏与聚会游戏扩展设计

日期：2026-09-09（设计）。2026-09-10 已实现文件映射、自由轮流投屏、谁是卧底与骰子猜点数；实际交付边界以 [IMPLEMENTATION.md](IMPLEMENTATION.md)、[SCREEN-SHARING.md](SCREEN-SHARING.md)、[GAMES.md](GAMES.md) 为准。下文仍保留原扩展规划，申请队列、审批、自动计时等不代表已经实现。

## 1. 结论与范围

三项需求均有实现路径。文件映射与游戏不需要新增运行服务；稳定的公网多人投屏需要媒体服务、HTTPS 和媒体网络配置。不能通过省略中继、限制为同一 Wi-Fi 或暗中减少观看人数，宣称完整投屏仍是原来的单端口部署。

“每个用户可以投屏”指每位有权限的参与者可以发起屏幕共享，默认轮流占用房间舞台，其他成员和独立大屏均可观看。多人同时发布、多画面并列是另一种模式，后续可增加；不是首版默认规则。

## 2. 存储映射

现有结构继续保留，避免无必要迁移：

```text
宿主机指定目录 → 容器 /data
  roomdeck.db           账号、房间、内容元数据、投票
  roomdeck.db-wal/shm   SQLite 运行时辅助文件（按实际存在）
  rooms/<room-id>/      原件、预览图、缩略图、导出 ZIP
  tmp/                 上传和导出处理中间文件
  .roomdeck.lock        单实例数据锁
  setup-token          仅未初始化时存在
```

文件对应关系为：房间 ID + 内容 ID + 变体 → 磁盘文件；数据库保存原文件名、类型、作者、时间、容量与可见性。采用 ID 避免同名覆盖、跨平台非法名称和路径注入。非文件内容保存在数据库，现有导出提供便签/链接 HTML、投票结果 JSON 和文件清单。

Compose 支持 `.env` 的 `ROOMDECK_DATA_PATH`；不设置继续使用旧命名卷。全目录映射避免只备份附件而遗失对应关系。不建议现在拆成多个挂载点：上传最终重命名与导出硬链接依赖文件系统特性，拆盘需要另外实现跨盘复制和独立磁盘余量检查。

后续可增加管理员“存储清单”下载，提供房间、原文件名、相对路径、大小和校验值，按数据库即时生成，不维护第二份容易失效的权威索引。挂载不改变到期删除语义；永久保留需要独立备份/保留策略。

## 3. 投屏交互与技术路线

房间新增“投屏 / Screen sharing”分类：舞台、当前分享者、开始共享、排队、停止和音量。每个参与者可申请；默认主持人批准，也可设置自由轮流。浏览器捕获必须由分享者点击触发：排队被批准后提示“现在开始”，再选择屏幕/窗口/标签页，不能后台自动开启。主持人可停止房间广播，但不能代替用户授权捕获。

大屏新增投屏模式，结束共享恢复此前照片/欢迎模式。黑屏关闭大屏的音视频播放；它与“结束所有人的投屏”是两个明确动作，后者撤销发布权限并关闭媒体会话。房间结束、分享者被移除、会话失效必须终止媒体授权。临时网络中断显示重连，超时释放舞台，不能永久占位。

推荐 WebRTC + 独立 LiveKit SFU 媒体服务：浏览器上行一份屏幕流，由媒体服务分发，Go 继续负责房间权限、排队和短时媒体凭证。避免一人向每个观众分别上传导致上行随观众数倍增。SFU 不默认录制或转码，投屏不写入照片目录、不计入文件配额、不进入 ZIP。

现有 WebSocket 只有失效通知，不能直接视为现成的投屏信令服务；媒体协商交给媒体 SDK，房间控制继续走 Go API。凭证仅绑定指定房间和身份，待批准用户没有发布权；大屏只有订阅权。服务端撤销必须同步到媒体服务，不能只等待凭证过期。建立发布租约与定期权限核验，应用失联时在限定时间内收回发布权限。

建议接口：申请/取消/批准/停止共享、获取受限媒体凭证、查询舞台。新增 `screen_sessions` 持久化控制状态，实际连接由媒体服务管理；重启后核对并终止陈旧会话，绝不自动恢复屏幕捕获。

初始目标 720p/15fps，可切 1080p；文字展示优先清晰度。音频根据浏览器实际捕获能力显示，不显示不存在的“已共享声音”。观看端提供点击播放以处理自动播放限制。正式参数需用真实设备与网络测试确定。

### 浏览器边界

网页屏幕捕获需要安全上下文和每次用户授权。部署给其他设备访问应使用受信任 HTTPS，不能将 localhost 的开发例外当成局域网 HTTP 能力。系统/窗口声音因浏览器和操作系统而异。

桌面浏览器作为首版发起端；手机观看须实测。移动浏览器不能承诺普遍支持整机屏幕共享，入口应检测能力并解释。若“每个用户”包含 iPhone/Android 必须能发起整机投屏，需要额外原生客户端和系统录屏扩展，增加客户端开发与分发工作；这不是 Docker 设置能解决的问题。浏览器大屏也不等同于电视原生 AirPlay/Miracast 接收器。

## 4. 游戏中心

房间新增“游戏 / Games”，与照片、文件、投屏并列。游戏库显示玩法、人数、时长；进入后加入座位、准备、查看私人身份、执行当前回合动作。默认一房一局，旁观者只看公开进度；可以继续分享照片与文件。

第一批建议谁是卧底、狼人杀，以及实现较轻的掷骰子/随机点名。游戏规则使用固定版本、自有中英词库和说明，不依赖外部服务。界面语言可以每人不同，牌组语言由本局统一选择，避免自动翻译造成词义线索不公平。

### 谁是卧底：先实现完整流程

准备 → 服务端随机发词 → 按座位描述 → 秘密投票 → 公布淘汰 → 判断胜负 → 下一轮/结算。词语只发给本人。首版固定规则：平票者加述后复投，再平票无人出局进入下一轮；平民清除全部卧底获胜，卧底人数达到剩余平民人数获胜。白板等变体后续作为独立规则开关。描述先按现场口头进行，远程语音需要另加音频房间能力，不能把投屏等同于语音聊天。

### 狼人杀：规则复杂，应独立里程碑

先固定一套可测试的 6 人规则：2 狼人、1 预言家、1 女巫、2 村民；女巫不能自救，同夜只能使用一瓶药，无警长和遗言技能。夜间按统一截止时间收集行动，统一结算死亡；白天发言、投票、平票复投一次，再平票无人出局。所有狼人死亡好人获胜；狼人存活人数达到好人人数狼人获胜。不是声称该变体是唯一官方规则。

采用系统法官；房主可以参赛但无权查看其他身份，另设主动选择的非参赛法官模式。预言家查验只返回给本人，狼人只获得规则允许的队友/行动信息，女巫只看到其阶段所需信息。游戏实现阶段还须细化空操作、断线、退出、夜间无击杀、全员死亡等规则表，再写状态转换测试。

### 服务端状态与保密

新增 `game_sessions`、`game_players`、`game_actions` 表，版本化规则和状态机。动作带唯一 ID 与预期回合版本，数据库事务保证重复提交不会重复投票/出牌。计时以服务端截止时间为准，客户端只负责显示。短暂断线保留座位；进程重启暂停未结束游戏，主持人确认继续，避免无人在线时自动结算。

公开进度与每位玩家私人视图使用独立响应模型；身份/词语不能先发送全量再在前端隐藏。大屏、观众、普通房间快照、日志、导出不包含未公开秘密。服务端随机分配，客户端不能提交身份结果。原有投票表不复用为游戏投票，避免规则和权限混淆。

游客会话保留时可重连；丢失会话不能只凭昵称领回身份。需要游戏专用的高熵恢复凭证或法官处理。设备失窃、玩家自行展示身份、服务器管理员读取数据库不在应用内保密保证范围。

## 5. 共存与部署

|改动|原有功能影响|部署影响|
|---|---|---|
|整目录映射|不改变上传、下载、导出、过期清理|增加可选路径与目录权限；已有数据需迁移|
|游戏中心|新增状态、私密视图、数据库迁移；保留现有投票|仍可一个 RoomDeck 容器，无必需外部服务|
|多人投屏|新增媒体流量和大屏模式；旧模块继续工作|媒体服务、HTTPS、UDP/TCP 与中继配置|
|手机整机投屏|需要原生发起端|额外客户端开发/分发，不只是服务端部署|

完整自托管建议提供配套 Compose：RoomDeck + LiveKit（内置 TURN）+ HTTPS 入口；已有反代可复用。单节点配置不预设 Redis 为必需依赖，多节点以后另议。固定镜像版本、自动生成服务密钥、提供配置检查和连接诊断，保持一次启动命令。但域名、公网可达地址、证书、媒体端口仍需正确准备；内网穿透仅支持 HTTP 时不足以保证媒体可达。

媒体端口、TURN/TLS 与 Web HTTPS 的 443 分配要在实现时给出明确拓扑（独立公网地址或合适的四层入口），不能简单将两个容器同时绑定宿主机 443。只有局域网或强限制网络也应验证中继路径；云媒体服务可省自建网络配置，但引入账号和费用，不作为默认必需。

媒体服务应独立健康检查，故障不阻塞 RoomDeck 启动和原有上传/游戏；投屏明确显示暂不可用。同一宿主机仍共享带宽/CPU，不能保证物理资源完全互不影响。按示例 2 Mbps 单流、20 人观看估算，媒体下行约 40 Mbps（另有协议开销），需要容量监控和合理限流。

数据库新增表采用顺序迁移；当前启动 schema 固定 `user_version=1`，必须先改为真正的版本迁移机制。升级前完整备份，不能用旧二进制直接打开未来新 schema 作为回滚。保持旧房间设置默认值与 API 行为，新增字段按兼容策略读取。

## 6. 实施与验收顺序

1. 文件映射配置与迁移说明（本次已完成配置，Docker 实机仍待验证）。
2. 数据库迁移框架、游戏公共/私人状态接口、谁是卧底完整闭环。
3. WebRTC 技术验证：真实双机 HTTPS、跨网 TURN、音频能力、手机观看；通过后完成投屏排队/授权/大屏恢复及完整部署模板。
4. 固定规则狼人杀、双语词库、重连恢复、小游戏扩展。

每阶段回归原有上传、成员撤销、投票、导出、房间关闭和到期。新测试必须覆盖跨房媒体凭证、被撤销后断流、大屏黑屏、游戏秘密不泄露、重复动作、计时竞态、旧数据库迁移和媒体故障时继续分享。完整上线前在 Docker 主机与真实手机/电视上验收，不以静态 UI 或模拟流作为投屏已完成的证明。
