# RoomDeck 下一阶段功能开发规划

日期：2026-09-11。本文保留规划基线；核心功能已开发，当前实际行为与差异见 [功能说明](FEATURES-2026-09.md)。下述时限、容量与性能指标中未被验证记录确认的部分仍是建议值和验收目标。

## 1. 范围与现状

本轮增加表情反应与弹幕、断线恢复与上传续传、投屏申请与排队，并完善大屏指定投票。保持中英双语、现有轻简风格与单套 Compose 部署。

| 功能 | 当前基础 | 本轮补齐 |
| --- | --- | --- |
| 表情与弹幕 | WebSocket 仅发送 refresh，客户端重新拉取快照 | 表情持久化、弹幕审核与短时事件分发 |
| 断线恢复 | 2–3 秒重连、20 秒轮询、保留最近快照 | 明确连接状态、退避重试、恢复对账与草稿保护 |
| 上传续传 | 整文件 XHR；失败重传，临时文件随请求清理 | 持久上传会话、分片校验、刷新/服务重启后续传 |
| 投屏排队 | 单发布者、多观看者，45 秒租约；占用时返回 SCREEN_BUSY | 申请、批准、队列、叫号与可靠交接 |
| 大屏投票 | 已有 poll 模式、display_target 和结果展示 | 选择器、一键上屏、目标失效处理、与投屏明确切换 |

重要现状：大屏快照目前只返回精选内容（照片自动上屏除外）；只设置 display_target 不足以展示未精选投票。启动逻辑目前会清空 tmp 和 reserved，因此不能把可续传文件直接放进现有 tmp。

## 2. 表情反应与弹幕

### 2.1 表情交互

- 照片、文件、便签、链接和投票卡片页脚增加一个表情入口，不挤占复制、下载等原有操作。
- 首版固定六种反应：喜欢、赞、哈哈、惊喜、鼓掌、庆祝。每人每条内容最多选择一种，再点取消，换一个替换；不做自由上传表情。
- 已有反应以“图标 + 数量”紧凑展示；按钮有中英文可访问名称、选中状态与至少 44px 点击区域。手机不依赖悬停。
- 点击可立即反馈，服务端失败则恢复并提示；请求使用“设置当前值”，不使用容易被重试反转的 toggle。
- 同一人的多标签页共用身份，不重复计数。展示汇总与自己的选择，默认不公开逐人反应名单。
- 主持人可关闭本房间反应；关闭时保留已有汇总、停止新增。隐藏/删除内容后停止展示或删除其反应。

### 2.2 弹幕交互与安全区

- 在分享入口新增“发弹幕”，输入框显示剩余字数，默认最多 60 个 Unicode 字符，按纯文本显示，不解析 HTML、链接或自定义样式。
- 主持人提供关闭、直接发送、审核后发送三种模式；新房间默认关闭，开启时建议审核后发送。
- 发送者收到“已发送 / 待审核 / 未通过 / 发送失败”，不把“进入队列”写成“已在大屏显示”。主持人可审核、拒绝、清空当前弹幕、禁言。
- 默认每人 5 秒一条、每分钟最多 10 条；房间每秒最多接纳 5 条，展示等待队列最多 20 条。超过上限明确拒绝，不无限堆积；这些值在压测后调整。
- **保护内容优先**：照片和欢迎页为弹幕预留独立底部横带，不覆盖照片正文、二维码或控制。投票页只在独立边栏显示静态短消息；投屏、游戏、黑屏、结束页默认不显示弹幕。
- 标准模式最多两条轨道，每条约 6–8 秒，按文本宽度排轨避免追尾。轨道层不接收点击；移动态只使用 transform。减少动态效果时改为静态消息轮换。
- 手机房间页显示可收起的静态互动列表，不让弹幕横穿按钮；屏幕阅读器不逐条强制播报全房间弹幕。
- 待审核消息 5 分钟过期；批准后分配事件 ID 和服务端展示期限，30 秒内未展示则丢弃。多块大屏尽量共享展示时间，不承诺逐帧同步。
- 首版不提供永久聊天记录；审核记录最长保留 24 小时或至房间删除，以先到者为准。关闭弹幕立即清空显示与待播队列。

## 3. 断线恢复与上传续传

### 3.1 房间恢复

统一显示“已连接 / 正在重连 / 网络已断开 / 正在同步 / 无权访问”。顶部使用紧凑提示条，保留最后一次内容；不反复弹通知，不清空用户正在填写的表单。

WebSocket 使用带随机抖动的指数退避，建议 1、2、4、8、16、30 秒封顶；online、返回可见页面时主动同步，避免重复建立连接。WebSocket 失败但快照成功时显示“实时连接恢复中”，不误报整个网络离线。

恢复流程：验证会话 → 拉取权威快照与版本 → 恢复可见内容/投票/队列 → 查询上传会话 → 恢复安全的重试。拒绝旧版本快照覆盖新状态。退出房间、被移除、房间删除后清理对应本地草稿和待处理请求。

- 同一浏览器且原会话仍有效时恢复原身份；清 Cookie 或换设备不保证恢复，不自动创建替代身份。
- 表单草稿以房间、身份为范围保存在本地；不缓存卧底词、LiveKit 令牌或其他人的私有游戏信息。共享设备可主动清除草稿。
- 不在离线状态自动排队投票、游戏操作、删除或投屏接管；这些操作依赖实时阶段，恢复后由用户确认。
- 表情设置、分片发送、上传完成等实现幂等后才允许自动重试。超时代表结果未知，先查询状态再决定重试。
- 不以“页面关闭后还能后台运行”为首版承诺，不新增 Service Worker 离线应用层。

### 3.2 上传体验

分享弹窗显示：准备文件 → 上传中 → 已暂停/等待网络 → 校验处理中 → 已完成。展示服务端确认的进度与当前传输进度，文件发送到 100% 后仍明确显示“正在处理”。

- 支持手动暂停、继续、取消、单项重试；关闭弹窗后上传继续，房间内有紧凑的任务入口。
- 当前页面仍持有 File 时网络恢复自动续传；刷新或重新打开后恢复任务清单，提示“重新选择原文件以继续”。第一版只在 IndexedDB 保存任务元信息，不默认复制整份文件到浏览器存储。
- 重新选择后检查大小、名称等提示信息，并通过分片摘要清单验证实际内容；不能仅凭同名同大小接着拼接。
- 维持现有限制：照片 20 MiB、文件 200 MiB、房间配额及图片解码限制。续传不等于放宽大小限制。

### 3.3 分片协议与持久化

建议固定 4 MiB 分片，每个文件串行发送、每个客户端最多两文件并行；服务端对房间、身份和全局设置活跃会话与处理并发上限。照片和文件共用新通道，旧整文件接口暂保留兼容，但所有限额必须共享。

1. 客户端在 Worker 中分片计算 SHA-256 清单（有界内存），初始化时提交清单、总大小、种类和客户端请求 ID。
2. 服务端验证写权限并预留配额与内容名额，返回绑定房间和上传者的 upload_id、已接收分片、过期时间。
3. PUT 指定分片；服务端检查索引、预期长度和摘要，落盘后确认。相同分片重传直接成功，内容不同返回冲突，不覆盖已有有效分片。
4. 全部分片齐全后 complete；唯一完成任务在受限工作队列中逐片合并、校验并执行原有 MIME、图片尺寸、预览图生成流程。
5. 内容元数据提交后返回同一个 content_id；响应丢失后再次 complete 或查询仍得到该结果，不生成两张照片。

新增 `/data/uploads/<room_id>/<upload_id>/`，由服务端生成路径；分片和中间文件不放入 tmp、不作为静态资源公开。会话保留至最后有效进度后 24 小时，且绝对寿命最多 72 小时、不得超过房间可写期限。取消、过期、关闭房间时回收文件与预留量。

数据一致性必须处理：

- `uploads` 与 `upload_parts` 持久化接收状态、哈希、大小、已预留字节、完成 content_id；预留统计启动时从有效会话重算，替换现有一律清零逻辑。
- 每片先写临时文件并校验，再原子重命名、登记数据库；启动时识别“文件已落盘但数据库未确认”等断点。已确认数据需按约定刷盘，不能仅留在进程缓冲区。
- 最终处理用独立 staging 目录；完成事务前后均可恢复。`reconcileFiles` 不能把正在完成的有效原文件当孤儿删除。
- 房间配额按最终内容预留，物理磁盘空间另外考虑合并期间“分片 + 成品 + 图片衍生文件”的峰值；避免只预留一份大小却写满磁盘。
- 服务重启可恢复上传，不自动恢复屏幕采集；损坏分片标记缺失并重新请求，不交付拼接错误的文件。
- 存储映射清单继续展示已完成文件；主持人的独立“未完成上传”区域显示占用、到期时间和取消入口，导出包不包含半成品。

## 4. 投屏申请与排队

### 4.1 模式与界面

保留单人发布、多端观看。新增三种房间模式：自由投屏（兼容现有）、先到先排、主持人审核。既有房间默认自由投屏，主持人可按活动切换。

参与者投屏页显示“当前由谁分享”“我的申请状态/前方人数”，提供申请、撤回、轮到我了开始分享。主持人显示待审批与候场列表，支持批准、拒绝、移除、叫下一位、结束当前投屏；首版不做拖拽任意排序。

**批准不是立即抢屏**：批准后进入 FIFO 候场，只有前一位结束并确认撤销媒体权限，才向下一位发出 30 秒叫号。被叫到的人必须主动点“开始分享”，并选择屏幕。浏览器要求屏幕采集由用户操作触发，授权不能永久复用，因此不能后台自动打开其屏幕。[MDN：getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)

### 4.2 状态与冲突

申请状态：pending → queued → offered → starting → presenting → finished；分支为 rejected、cancelled、expired、failed。房间同时只能有一个有效 offered/starting/presenting 占位；每个身份最多一条活跃申请。

- 叫号仅面向近期在线者；短暂断线保留顺序 60 秒，超时标记离线并跳过。重新上线需明确重新加入队尾，不突然抢回已交出的席位。
- 点击开始时先同步触发屏幕选择；授权后使用短期 offer ID 申请服务端原子占位。若已过期/被撤回，立即停止本地 tracks，不能发布。
- 浏览器取消选择时可在叫号有效期内重试；进入 starting 后限 30 秒建立发布连接，失败回收占位。
- 活跃发布继续沿用 45 秒租约及真实媒体连接检查；仅页面在线不能续租。重复点击、两个标签页和主持人并发操作通过版本与事务处理。
- 主持人强制结束后确认 LiveKit 撤权成功才叫下一人。媒体服务不可用时显示交接失败，保持禁止新发布，恢复后重新核实状态。
- 服务重启将 pending/queued 保留并重新检查身份和在线状态；offered/starting 失效，presenting 标记中断。重启后由主持人继续叫号，不自动采集。
- 禁言/移除、房间关闭、投屏关闭会撤销对应申请与发布权限。模式切换时明确提示并取消旧排队，但不无提示地切断正在分享者。

## 5. 大屏选择当前投票

### 5.1 主持人操作

大屏控制区选择“投票”后，展开投票选择器：题目、进行中/已结束、是否隐藏结果、当前上屏标记。默认优先展示进行中的投票供选择；没有可选项时提供创建投票入口。

每张投票卡片的主持人菜单增加“在大屏显示”，一键设置模式和目标。控制区同步显示选中题目、状态和切换按钮；多端主持人按版本保存，冲突时刷新并提示，避免覆盖彼此设置。

### 5.2 显示与隐私规则

- 显示题目、所有选项、投票进行状态及参与入口。未公开结果时仍显示选项，只隐藏票数和占比；结束后按原有规则展示结果。
- 上屏只允许同房间、可见且 poll 模块开启的投票。独立上屏动作以事务设置 selected=true、display_mode=poll、display_target=id，保持当前大屏精选过滤规则一致；明确标记该投票已精选。
- 隐藏、删除或取消精选当前投票后，清除目标并进入“等待主持人选择投票”，不得静默切到另一题。已结束的题目可继续展示结果。
- 大屏数据只包含允许展示的信息；隐藏结果必须在服务端移除，不能只是前端遮住。不得下发逐人选票、私有游戏信息或投票者身份。
- 多选投票占比为“选择该项的人数 / 投票人数”，注明多选、各项合计可能超过 100%；零票时不出现 NaN。
- 长题目换行，较多选项使用适合电视的双列布局；在当前允许的最大选项数和文字长度下测试，不依赖现场人员滚动大屏。

### 5.3 与屏幕分享的优先级

当前大屏会自动加载屏幕分享，因此需要增加明确的舞台来源 `display_source=content|screen`，与内容模式分开：

- 活跃分享开始时允许切到 screen；主持人“一键展示投票”则切到 content，正在分享者仍可供房间成员观看。
- 控制区显示“当前大屏：投票 / 某人的屏幕”，提供返回投屏按钮；不能出现选了投票却被视频层盖住的情况。
- screen 结束后返回已保存的内容模式与投票目标；房间结束、黑屏、会话失效优先级最高，屏幕与弹幕均停止展示。
- display 观看令牌与后端媒体权限同步检查来源；切到 content 后大屏退出媒体订阅。其他成员观看不受影响。

## 6. 实时通道、接口与代码边界

持久状态依然以数据库为准。新增事件信封 `{type,event_id,state_revision,emitted_at,payload}`；客户端识别版本并保留旧 refresh 兼容。现有 rooms.version 主要用于设置编辑冲突，不能代表全部内容变化；新增持久 state_revision，在内容、选票、反应、队列等可见状态变更的同一事务中递增，快照在一致性读事务中携带该值。设置保存继续使用原 version，避免一次表情操作让主持人设置表单失效。持久变更合并通知、按模块刷新，表情点击不得让全房间反复拉取完整照片/投票快照。

弹幕使用独立、有界的短时队列，不能沿用容量为 1 的 refresh 通知槽直接传消息。采用“最多显示一次”的目标：事件 ID 去重、到期丢弃，重连只收仍有效的消息，不补播一整段历史。审核消息可持久化，但 pending 内容只推给主持人和发送者；公共大屏只接收已批准且有效内容。事件通道断开时允许安全降级，不能把待审核文本塞入全员快照。

| 资源（均在 /api/v1/rooms/:room 下） | 建议接口 |
| --- | --- |
| 反应 | PUT/DELETE /contents/:id/reaction；GET /reactions?ids=... |
| 弹幕 | POST /danmaku；GET /danmaku（按角色过滤）；POST /danmaku/:id/moderate；POST /danmaku/clear |
| 上传 | POST/GET /uploads；GET/DELETE /uploads/:id；PUT /uploads/:id/parts/:index；POST /uploads/:id/complete |
| 投屏队列 | POST/GET /screen/requests；DELETE /screen/requests/:id；POST /screen/requests/:id/approve 或 reject；POST /screen/next |
| 大屏控制 | POST /display/control，带 expected_version、mode、target、source |

所有写接口继承同源检查、角色、会话、禁言与房间状态校验；大屏角色只读。客户端幂等键以身份、房间和操作范围约束，防止跨用户查询或复用结果。限流拆分初始化、分片、完成、弹幕，避免现有“上传每分钟 30 次”把正常分片误拦。

建议新增 Go 模块 `reactions.go`、`danmaku.go`、`uploads.go`、`screen_queue.go`、`display.go`；复用 assets.go 的校验/成品发布流程，避免维护两套。前端拆为 ReactionBar、DanmakuComposer、DanmakuLayer、UploadTasks、ScreenQueue、DisplayPollPicker；同步逻辑扩展 roomSync.ts，上传队列独立 composable。

迁移新增 reactions、danmaku_messages、uploads、upload_parts、screen_requests，必要的幂等记录与 room settings 字段；数据库当前版本为 2，按发布阶段递增迁移。每张表明确房间删除级联、唯一约束、时间/状态索引与清理任务。先实现恢复规则，再启用新写入路径。

中英文同时交付：全部按钮、状态、空态、错误、审核和数量文案使用翻译键；英文长文案、手机安全区、键盘焦点与减少动态效果纳入验收。

## 7. 对原功能和部署的影响

| 项目 | 影响与处理 |
| --- | --- |
| Compose | 维持 RoomDeck + LiveKit + media-init；无需 Redis、消息队列、对象存储、新端口或外部审核服务 |
| 文件映射 | 原 ROOMDECK_DATA_PATH:/data 不变；uploads 子目录随现有映射持久化，不放容器临时层 |
| 资源 | 分片合并增加临时磁盘和 I/O；弹幕增加有限 WebSocket 流量；投屏排队本身不增加视频流数 |
| 数据升级 | 自动迁移，升级前备份完整数据目录；新版库可能被旧版拒绝打开，回滚需恢复匹配备份与镜像，不能仅换旧镜像 |
| 原照片/文件 | 原下载路径和映射清单保持有效，新增上传路径最终生成同样的成品结构 |
| 投票与游戏 | 不改变计票和游戏规则；重点回归隐藏结果、投票截止和私有词隔离 |
| 投屏 | 保留自由模式，新增排队模式；大屏来源切换是有意的行为改动，必须三端联调 |
| 实例数量 | 延续当前单 RoomDeck 实例和独占数据目录，不承诺多副本共享 SQLite；扩容另行设计 |

因此部署步骤预计基本不增加，但程序内部复杂度明显增加，尤其是上传崩溃恢复与投屏交接。HTTPS、跨网 TURN 等现有条件仍适用；需在有 Docker 的环境完成最终容器重启与映射验收。

## 8. 实施顺序与验收门槛

### 阶段一：恢复与事件基础
连接状态、版本对账、退避、事件分流、身份隔离、终止态处理；旧客户端仍能接收 refresh。模拟断网/服务器重启后，不丢草稿、不覆盖新状态、不重放游戏操作。

### 阶段二：指定投票上屏
选择器、一键上屏、服务端目标校验与舞台来源切换。双主持人、参与者、两块大屏联调：目标一致、隐藏结果不泄露、删除后不切错题、投屏不遮挡投票。

### 阶段三：上传续传
先交付会话与分片、恢复对账，再接入 UI。对上传中、合并中、成品已写但事务未完成、事务完成但响应丢失分别注入中断；最终文件哈希一致、只生成一条内容、配额无泄漏。测试刷新重选、错误原文件、取消与完成竞态、磁盘不足、房间关闭及容器重启。

### 阶段四：投屏排队
验证重复申请、多人同时开始、取消授权、叫号超时、离线跳过、强制撤权失败和服务重启。任何情况下只允许一个有效发布者；旧发布者不能靠旧令牌重新加入。

### 阶段五：反应与弹幕
反应幂等、审核隔离、清屏、限流、过期去重、减少动态效果。建议以默认 50 人房间、2 块大屏进行约定硬件下压测，目标为正常负载下持久状态 95% 在 1 秒内同步；记录实际结果后再决定上限，不提前宣传容量保证。

### 发布门槛
中英文桌面/手机布局、自动无障碍检查与键盘手测；原内容、投票、游戏、上传、多人观看回归通过；Docker 映射、重启、备份恢复通过。必须特别核对：弹幕不挡字、不截获点击，断网后已结束的投票与游戏不能继续提交，未完成文件不会进入导出包。

## 9. 浏览器边界依据

- 屏幕分享需用户主动触发，权限不能持久复用：[MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia)。据此设计“叫号后点开始”，不承诺自动接管屏幕。
- 网页通过用户选择获取文件：[MDN File API](https://developer.mozilla.org/en-US/docs/Web/API/File_API/Using_files_from_web_applications)。本方案选择只缓存元信息，因此刷新后需要重新选择原文件；原生文件句柄持久化可作为后续增强，不作为跨浏览器续传前提。
